# RCA — digihome.no serving a stale build (missing public/team assets)

**Deployment:** hero-premiere-4 (custom domains digihome.no, www.digihome.no)
**Template:** nextjs_mongo_shadcn_base_image — Next.js, `frontend_type: kubernetes` (frontend served by the K8s pod, NOT Cloudflare R2/KV)
**Active run:** 8cb53bb2-5b44-4956-be65-7e14390d487e (redeploy, success, built 2026-10-05 17:28:59→17:31:19 UTC, promoted 17:32:15)
**Prior deploy today:** 19ab9a48-1fa2-492c-96db-705cbe4160e5 (redeploy, success, built 17:08:59→17:14:21)

## Questions answered

### (1) Did today's two deploys succeed, or did the build fail and leave the old image running?
They **succeeded**. Both runs completed every step green: `wakeup → build → mongodb_migrate → manage_secrets → deploy → health_check`. Critically, the **build step actually RAN both times** (active run's build took ~2.5 min, 17:28:59→17:31:19) — this was NOT a "source unchanged, reuse previous image" skip. A fresh image was built, pushed, deployed and promoted each time. Build state = SUCCESS, image pushed (`sha256:21e6c20b...`). So the "build failed, previous image kept serving" hypothesis is **ruled out**.

### (2) Which snapshot the live pod was built from
The live image was built from a **source snapshot that predates today's 08:55–09:12 UTC changes**, even though the builds themselves ran at 17:08 and 17:28. Proof is the content the live pod serves (see origin probe below): the new files are absent and `jens-petter-glittenberg.webp` is the OLD 13146-byte version, not today's 35298-byte version.

Important mechanism: the Emergent deployer's `pull_source` step does **not** do a `git checkout`. It takes a filesystem dump of the agent-env / preview pod's working directory. So "git HEAD (b0843f5) has the files" and "the deployed snapshot has the files" are two different things. The deployed image reflects what was on the preview pod's disk at pull time — and that disk state was stale relative to git HEAD.

(I could not list the pulled snapshot's files directly — the eph debug sandbox returned repeated server-side 500s, `container not found (main)` / `cannot exec in a deleted state`. The origin probe below is conclusive without it.)

### (3) Build logs
Build SUCCESS, no errors. Image built and pushed cleanly (Cloud Build id 4db5e6df-ff3f-48b3-96f6-53cf8c1a07cd). No failure signal. The problem is upstream of the build (what source it was handed), not the build itself.

### (4) Could a CDN/edge layer still be pinned to an old origin?
**No.** I probed the K8s origin directly via `hero-premiere-4.emergent.host`, which bypasses Cloudflare completely (digihome.no proxies through Cloudflare; emergent.host is the direct ingress to the pod):

| Path | digihome.no (via Cloudflare) | hero-premiere-4.emergent.host (ORIGIN) |
|---|---|---|
| /team/martin-vikesland.webp | 404 `{"error":"Ikke funnet"}` | **404** `{"error":"Ikke funnet"}` |
| /team/oyvind-storli-hoel.webp | 404 | **404** |
| /team/jens-petter-glittenberg.webp | 200, 13146 B (old) | **200** (old file) |
| /team/kevin-ai-v2.webp | 200 | **200** |

The 404s are identical at origin. Cloudflare is faithfully serving what the pod returns — the edge is NOT pinned to anything. This is 100% a stale-image problem, not a CDN problem.

## Root cause
Both of today's deploys built fresh images, but from a **stale source snapshot**: the agent-env/preview pod filesystem that `pull_source` dumped did not contain today's 08:55–09:12 updates to `public/team/` (martin-vikesland.webp, oyvind-storli-hoel.webp were absent; jens-petter-glittenberg.webp was the pre-08:55 13146-byte version). The files exist in git HEAD and in the user's local working tree, but the deployer builds from the preview pod's disk, not from git — so the committed-but-not-present-on-preview-disk files never made it into the image.

The fact that **two independent re-pulls (17:08 and 17:28) both produced the same stale content** is the key signal: a one-off pull glitch would not repeat identically. This points to the files genuinely not being present in the workspace the deployer reads from at deploy time — i.e. a divergence between where the files were committed (git HEAD / local) and the Emergent preview workspace that gets deployed.

## What is needed to fix it (so the live site serves martin-vikesland.webp + oyvind-storli-hoel.webp)
1. **Verify presence in the Emergent preview/agent-env workspace that actually gets deployed** (not a local machine): in that environment run `ls -la public/team/ && wc -c public/team/martin-vikesland.webp public/team/oyvind-storli-hoel.webp public/team/jens-petter-glittenberg.webp`. Expected: martin=85652, oyvind=41042, jens-petter=35298. If any are missing/old there, that is exactly why the pull was stale — restore/copy the files into that workspace (a `git checkout HEAD -- public/team/` or re-sync from the asset commit b0843f5 inside the preview environment).
2. **Redeploy** once the preview workspace is confirmed to physically hold the correct files. A redeploy re-pulls and rebuilds; since the build is not being skipped here, a correct snapshot will produce a correct image.
3. **Verify after redeploy** against the ORIGIN (bypassing Cloudflare): `curl -I https://hero-premiere-4.emergent.host/team/martin-vikesland.webp` should be 200. Then purge/cache-bust on digihome.no.
4. **If step 1 shows the files ARE present in the preview workspace and a fresh redeploy still ships stale content**, then `pull_source` is snapshotting a stale/cached copy — that is a platform bug to escalate with these two run ids (19ab9a48, 8cb53bb2) and job 0368ea04-032a-406b-9ed9-718b09007a58.

## Side note
`yarn.lock` being untracked does not cause this — it does not affect how `public/` static assets are copied, and old public assets (kevin-ai-v2.webp) serve fine. Not the cause. Recommend committing yarn.lock for reproducible installs, but it is unrelated to the missing images.
